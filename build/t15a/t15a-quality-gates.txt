過程中發現並修正的 2 個 bug（實跑抓到，非憑空聲稱）
====================================================================
1. 【CLI 層級的真實 bug，離線測試測不出，靠 CLI smoke test 抓到】station5-check.ps1 dot-source
   ../t10/gate-reset.ps1 -FunctionsOnly 與本目錄 station5-dispatch-prep.ps1 -FunctionsOnly 時，
   兩個被 dot-source 的腳本各自也宣告了同名參數 `$FunctionsOnly`；dot-source 與呼叫端共用同一層
   作用域，被 dot-source 腳本自己的 param 綁定會覆蓋呼叫端已綁定好的同名變數。結果：直接執行
   `.\station5-check.ps1 -SubmissionPath ... -Repo ... -Issue ...`（不帶 -FunctionsOnly）時，
   本檔自己的 $FunctionsOnly 在兩次 dot-source 後被覆蓋成 $true，導致 CLI 主流程被跳過——
   無輸出、exit 0，看起來像「什麼都沒做但也沒報錯」，比顯式報錯更危險。修法：在任何 dot-source
   之前，先把呼叫端原始意圖存進獨有變數名 `$T15aRequestedFunctionsOnly = $FunctionsOnly.IsPresent`，
   底部一律讀這個變數。修正後以 `.\station5-check.ps1 -SubmissionPath fixtures\executor-is-
   verifier.json -Repo o/r -Issue 1`（FAIL 案例）與 `...\valid-submission.json`（PASS 案例，
   正確推進到讀 PAT 檔那一步才因沙盒無真實 PAT 而報錯，證明前面的十項查核邏輯確實跑過）兩種
   情境重跑，行為皆恢復正常。
2. Test-PromptTextMarkers 初版採「命中任一樣式即拒絕」，用真實內容（T-11 smell 基線 asset 頁尾
   引用「Spec_station-command_v1.5.md」作為出處註記；Spec §5.2 條文本身談到「12 條 Fowler smell
   基線」時提及一次 "Fowler"）實跑後發現兩處合理誤傷——單一字樣命中不足以區分「合法提及」與
   「真的整段夾帶」。修法：改採門檻計數（須命中 ≥2 個不同樣式才判定為疑似洩漏），並同步調整
   station5-dispatch-prep.ps1 CLI 模式的預設 spec 摘錄邏輯（不再預設灌入整份 spec 檔，改截取
   anchor 段落附近固定字數，貼近實際 dispatch 用法）。修正後 N3／N4（真實內容）與 N5／N6
   （人為污染，正面偵測力驗證）四項皆綠，CLI 預設呼叫（不帶任何摘錄參數）亦轉為 PASS。

  真正的硬保證；第二道防線的角色是「抓得到就多一層防線，抓不到不代表乾淨」，此為明確的已知限制。

  plugin repo DECISIONS.md 判定——理由：本票 scope 是站5票級審查編排，讀 DECISIONS.md 屬 gate
  既有職責（../t10/），Commander 在呼叫本檔前應先查過 DECISIONS.md 並把結論填入交件欄位，
  避免重複實作同一份讀取邏輯（DRY，同 T-10 對 all.decisions-exemption 的既有處理方式）。
- 實際 dispatch（Task 呼叫兩個平行 fresh-context general-purpose sub-agent）是 Commander 的
  動作，本票不代為呼叫（同 T-12 run-dispatch.ps1 的既有先例）；station5-dispatch-prep.ps1 只
  負責組 prompt 文字與寫證據檔，station5-check.ps1 只負責驗證 Commander 取回的兩份報告。
- Test-PromptTextMarkers／Test-AxisInputSeparation 的樣式庫涵蓋已知常見洩漏型態，無法涵蓋所有
  可能的夾帶手法（例如刻意拆散關鍵詞、以圖片或編碼規避）；未命中已知樣式時，結構性 kind 白名單
  仍是第一道且更可靠的防線。
